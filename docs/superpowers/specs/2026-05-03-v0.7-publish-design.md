# v0.7 — Publish: design spec

**Status:** Draft (2026-05-03)
**Predecessor:** [v0.6 OAuth 2.1 Resource Server](./2026-05-02-v0.6-oauth-design.md)
**Roadmap line:** "v0.7 — Publish. Submit to the public MCP registry. Real users."

## Goal

Make sky-tonight a server that anyone — not just the author on their own machine — can install from the public MCP registry and use against a hosted instance. Three concerns ship together:

1. **Publish.** Submit a `server.json` to the public MCP registry under namespace `io.github.girishbaranda/sky-tonight`. Stand up a hosted endpoint at `https://sky-tonight.techplanner.xyz/mcp`. Ship a Dockerfile + `fly.toml` recipe so any self-hoster can copy our deploy.
2. **Postgres.** A second storage backend behind the same `logObservation` / `recallObservations` interface, selected at process start by the presence of `DATABASE_URL`. SQLite remains the default for local dev and stdio; Postgres is required for the hosted instance and recommended for any multi-user self-host.
3. **Scope enforcement.** The `sky-tonight:read` and `sky-tonight:write` scopes that v0.6's PRM document already advertises now actually gate calls. Scope-aware errors carry RFC 6750-shaped `WWW-Authenticate` headers so MCP clients can transparently re-do the OAuth flow asking for the missing scope.

The stdio path stays unchanged: SQLite, no token, no scopes, single-user (`"local"`). v0.7 only changes the HTTP path's auth/storage and adds a deploy story.

## Out of scope

Recorded explicitly so they don't sneak in:

- **Token issuance, refresh, revocation, audit logs.** Logto handles all of this. We are still purely a Resource Server.
- **Per-user quotas / rate limits.** No abuse vector worth solving for v0.7's expected scale.
- **A web UI for browsing one's own observation log.** Out of project scope.
- **Stdio transport changes of any kind.** Stdio stays exactly as v0.6 left it.
- **New tools, prompts, or resources.** v0.7 publishes what we have, doesn't extend it.
- **Migrating existing user data between machines.** Local SQLite `local`-scoped rows on a v0.6 user's laptop don't roam to the hosted Postgres. If anyone asks, that's a separate "data import" story.
- **JSONB indexes on observation notes.** Notes stay `TEXT` in Postgres for parity with SQLite; revisit only if a search use case shows up.
- **Multi-region Postgres / Fly app replication.** Single primary, single region. v0.7 is personal-grade.
- **Self-host of Logto.** Logto Cloud only. Self-hosting Logto is a real escape hatch for v0.8+ but not now.

## Architecture overview

Five components, all of them new to v0.7 except sky-tonight itself:

```
                                                ┌──────────────────────┐
                                                │  Logto Cloud (AS)    │
                                                │  - issues JWTs       │
                                                │  - DCR for clients   │
                                                │  - JWKS              │
                                                └──────────┬───────────┘
                                                           │ token
                                                           ▼
┌──────────────┐    HTTPS    ┌─────────────────────────────────────────┐    SQL    ┌────────────────┐
│  MCP client  │ ─────────►  │  sky-tonight.techplanner.xyz            │ ────────► │  Neon Postgres │
│  (Claude     │   Bearer    │  - Fly.io machine, Docker, Node 22      │           │  (managed)     │
│   Desktop /  │   JWT       │  - src/http.ts + verifyBearer + scope   │           └────────────────┘
│   Cursor /   │             │  - observation-log lib (PG backend)     │
│   etc.)      │             └─────────────────────────────────────────┘
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  MCP         │
│  Registry    │  ←── server.json submission, namespace io.github.girishbaranda/sky-tonight
│  (public)    │
└──────────────┘
```

**The flow for a real user:**

1. Adds sky-tonight to their MCP client via the registry (paste the registry name into Claude Desktop, Cursor, etc.).
2. Client makes the first `POST /mcp` request without a token. Server returns 401 with `WWW-Authenticate: Bearer ..., resource_metadata="https://sky-tonight.techplanner.xyz/.well-known/oauth-protected-resource"`.
3. Client fetches the PRM doc, discovers Logto as the AS, runs Dynamic Client Registration to register itself, then runs an OAuth 2.1 + PKCE flow asking for `sky-tonight:read`.
4. User signs into Logto in a browser window the client opens.
5. Client receives a JWT, retries `POST /mcp` with the bearer token. Reads work. Writes return `-32001` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="sky-tonight:write"`. The client re-asks the user to authorize the write scope (typically a one-click step), gets a new token, retries. Future writes succeed.

## Mechanical choices (locked)

These were decided during brainstorming. Listed here as the source of truth; downstream sections build on them.

**M1 — Scope grant.** Logto registers an API resource for `https://sky-tonight.techplanner.xyz` with two scopes:

| MCP method | Required scope |
|---|---|
| `tools/list`, `resources/list`, `resources/read`, `prompts/list`, `prompts/get` | `sky-tonight:read` |
| `tools/call` for `whats_visible_tonight`, `next_iss_pass`, `moon_phase`, `deep_sky_visible_tonight`, `recall_log` | `sky-tonight:read` |
| `tools/call` for `log_observation` | `sky-tonight:write` |
| `initialize`, `ping`, `notifications/*` | none (any valid token, including zero-scope, passes) |

Note that "none" here means *no specific scope required*, not *no token required*. Over HTTP, every request still needs a valid Bearer JWT (v0.6 invariant); the scope-free rows just don't add a further scope check on top.

Missing scope → JSON-RPC error `-32001`, message `"insufficient_scope"`, `data: { required_scope: "sky-tonight:write" }`. HTTP response carries `WWW-Authenticate: Bearer error="insufficient_scope", scope="sky-tonight:write", resource_metadata="…"` per RFC 6750 §3.

Stdio is untouched. No token, no scopes, no checks. Internally the dispatcher treats stdio as "all scopes granted" so the dispatch logic stays uniform, but the check short-circuits when no token was presented.

**M2 — Backend selection.** Single env-var switch in [src/lib/observation-log.ts](../../../src/lib/observation-log.ts):

- `DATABASE_URL` set → Postgres backend (new `pg`-based path).
- `DATABASE_URL` unset → SQLite backend (existing v0.6 path), gated by `SKY_TONIGHT_DB` as today.

`logObservation()` / `recallObservations()` signatures unchanged. Both backends share a single migration set. Hosted instance always sets `DATABASE_URL`; local dev / stdio / self-host single-user defaults to SQLite.

**M3 — Migrations.** Replace v0.6's boot-time `CREATE TABLE IF NOT EXISTS … ALTER TABLE … ADD COLUMN` with a numbered `migrations/` folder. Each migration is engine-scoped: `001_init.sqlite.sql` and `001_init.postgres.sql`, etc. A tiny in-process runner applies pending migrations under a transaction on boot, recording state in a `_migrations(version INTEGER PRIMARY KEY, applied_at)` table. New databases get the full set; existing v0.6 SQLite databases get stamped to the current version (without re-applying DDL) by inspecting their existing schema. Boot-time, no separate `migrate` command.

**M4 — Registry submission.** One `server.json` at the repo root, namespace `io.github.girishbaranda/sky-tonight`, two `packages` entries: an `npm` entry for stdio and a `remote` entry for the hosted HTTPS URL. Submission via the `mcp-publisher` CLI authenticated with GitHub.

## Code changes

Three code-level work items in sky-tonight itself. None of them touches stdio. All of them are env-var-gated so the lib stays a clean drop-in for self-hosters.

### Backend abstraction in `src/lib/observation-log.ts`

Today: this file imports `better-sqlite3` directly and contains SQL strings inline. v0.7 splits it into:

- **`src/lib/observation-log.ts`** — public surface (`logObservation`, `recallObservations`). Picks a backend at module-init time based on `DATABASE_URL` presence and dispatches all calls through it. Public types and validation stay here. **No SQL in this file anymore.**
- **`src/lib/observation-log/backend.ts`** — TypeScript interface: `{ insert(row), query(filters), close() }`. Both backends implement this. Intentionally narrow — no transactions, no streaming, no abstractions we don't need today.
- **`src/lib/observation-log/sqlite.ts`** — the existing v0.6 implementation, mechanically lifted out. `better-sqlite3` import lives only here.
- **`src/lib/observation-log/postgres.ts`** — new. Uses `pg` (node-postgres). One persistent `Pool` per process. Same SQL semantics as SQLite, with Postgres-native types: `TEXT`, `TIMESTAMPTZ`, `TEXT` for notes (parity with SQLite — JSONB deferred).

Why this shape: the public file has no SQL; engine files have no validation. A future v0.8 (different storage entirely, scope-by-resource pruning, etc.) edits only the engine file or the runner. Two engine files is the "rule of three minus one" — once we add a third we'll abstract; until then this is the right amount of structure.

### Migration runner

A new `src/lib/observation-log/migrations.ts`. Reads SQL files from a `migrations/` folder shipped in the package, applies any unrecorded ones in numeric order under a transaction, records each in `_migrations`.

**File layout:**

```
migrations/
  001_init.sqlite.sql
  001_init.postgres.sql
  002_add_user_id.sqlite.sql
  002_add_user_id.postgres.sql
```

Two file extensions per version because syntax differs between engines (`INTEGER PRIMARY KEY AUTOINCREMENT` vs `BIGSERIAL`, etc.). When a migration's DDL is identical between engines we still ship two files — the duplication is cheap and makes the runner trivial.

**Bootstrap detection.** On first run against an *existing* v0.6 SQLite database, the runner sees an `observations` table without a `_migrations` table. It inspects the schema (does `user_id` exist?) and stamps `_migrations` with the corresponding version *without re-running* the DDL. New databases (SQLite or PG) run all migrations from scratch. Existing v0.6 self-hosters upgrade and keep their data; no manual step.

**Failure mode.** Migration failure aborts process startup with a clear error. We don't want a half-migrated DB silently accepting writes. Fly's healthcheck catches this and the previous machine version stays serving.

### Scope enforcement in `src/http.ts`

Today: `verifyBearer` validates the JWT's signature, issuer, audience, and `sub`. v0.7 extends this to also extract the `scope` claim (space-separated string per RFC 6749) into the per-request user context. The MCP server's request handler in `createMcpServer` then checks the required scope against the granted scopes before dispatching the call.

The check happens *after* JSON-RPC parsing but *before* tool dispatch — the existing `runWithUser` from v0.6 carries the user id and now also carries the scope set. The dispatch-level check is driven by a single static map from MCP method name (and tool name, for `tools/call`) to required scope, declared in one place in `src/http.ts`. Each handler stays ignorant of scopes, matching v0.6's "auth lives at the boundary" pattern.

On missing scope: respond with JSON-RPC error code `-32001`, message `"insufficient_scope"`, `data: { required_scope: "sky-tonight:write" }`. The HTTP response carries `WWW-Authenticate: Bearer error="insufficient_scope", scope="sky-tonight:write", resource_metadata="…"` per RFC 6750 §3.

## Operations

All steps below happen in the **last** sequence, after every code change in the previous section has merged to `main`. None of it requires the user to be online for ongoing maintenance.

### Logto Cloud tenant

1. Sign up for Logto Cloud, create a tenant `sky-tonight`.
2. **API resource:** add resource `https://sky-tonight.techplanner.xyz` (the `aud` claim our server expects). Define two scopes on it: `sky-tonight:read`, `sky-tonight:write`.
3. **Application:** create a public OAuth client with PKCE enabled. Enable Dynamic Client Registration on the tenant — that's what lets MCP clients self-register without us pre-provisioning each user's client.
4. **Sign-in experience:** enable email + password (and optionally Google/GitHub social) so end users can self-onboard. No invite-only / org gating.
5. Capture: `OAUTH_ISSUER` (e.g. `https://<tenant>.logto.app/oidc`), `OAUTH_AUDIENCE` (`https://sky-tonight.techplanner.xyz`), `OAUTH_JWKS_URL` (`<issuer>/.well-known/jwks.json`). These are the env vars v0.6's `loadAuthConfig` already reads.

### Neon Postgres

1. Create a Neon project `sky-tonight-prod`. Default region paired with our Fly region (both in IAD).
2. Branch `main`, single database `sky_tonight`. No special extensions in v0.7.
3. Copy the *pooled* connection string into `DATABASE_URL`. Fly machines connect over plaintext within Neon's TLS-terminated edge.

### Fly.io app

1. `flyctl launch --no-deploy` from the repo. Generates a baseline `fly.toml` we then edit.
2. **Dockerfile** — multi-stage:
   - Stage 1 (`node:22-slim`): `npm ci`, `npm run build`. Includes `better-sqlite3`'s native compile so the same image works for self-hosters who don't set `DATABASE_URL`.
   - Stage 2 (`node:22-slim`): copy `dist/`, `node_modules/`, `package.json`, `migrations/`. Run as non-root. `CMD ["node", "dist/http.js"]`.
3. **`fly.toml`**: app name `sky-tonight`, primary region `iad`, internal port `3000`, HTTPS handler with `force_https = true`, `auto_stop_machines = "stop"` + `min_machines_running = 0` for scale-to-zero. One machine, `shared-cpu-1x`, 256 MB.
4. **Secrets** via `flyctl secrets set`: `DATABASE_URL`, `OAUTH_ISSUER`, `OAUTH_AUDIENCE`, `OAUTH_JWKS_URL`, `PUBLIC_URL=https://sky-tonight.techplanner.xyz`. No `DEV_JWT_SECRET` in production.
5. `flyctl deploy`. First deploy runs migrations against Neon on boot.

### DNS

1. CNAME `sky-tonight.techplanner.xyz` → `sky-tonight.fly.dev` at the registrar.
2. `flyctl certs create sky-tonight.techplanner.xyz`. Fly issues a Let's Encrypt cert within ~1–2 minutes after DNS propagates.
3. Smoke test: `curl https://sky-tonight.techplanner.xyz/.well-known/oauth-protected-resource` returns the PRM JSON with `resource: "https://sky-tonight.techplanner.xyz"` and `authorization_servers: ["<logto-issuer>"]`.

### npm publish

1. `package.json` `name` is currently `sky-tonight`. Verify availability on npm — if taken by anyone other than this account, rename to `@girishbaranda/sky-tonight` and update the registry entry's package reference.
2. `bin` already points at `dist/server.js` (stdio). Add `prepublishOnly` running `npm run build`.
3. `files` field in `package.json` listing `dist/`, `migrations/`, `LICENSE`, `README.md`. Excludes `src/`, tests, scripts.
4. `npm publish` (with 2FA). Tag the release `v0.7.0` in git.

### MCP registry submission

1. Author `server.json` at the repo root, namespace `io.github.girishbaranda/sky-tonight`. Two `packages` entries:
   - `{ "registry": "npm", "name": "sky-tonight", "version": "0.7.0", "transport": { "type": "stdio" } }`
   - `{ "registry": "remote", "url": "https://sky-tonight.techplanner.xyz/mcp", "transport": { "type": "streamable-http" } }`
2. Install `mcp-publisher` CLI. Authenticate via GitHub. Namespace `io.github.girishbaranda/*` is owned by the GitHub user `girishbaranda`.
3. `mcp-publisher publish ./server.json`.

## Test plan

Tests stay light — handful of unit tests per lib file plus the end-to-end smoke script.

| Layer | What we test | Where |
|---|---|---|
| Migration runner | Empty SQLite → all migrations applied; v0.6 SQLite (has `observations` w/ `user_id`, no `_migrations`) → stamped to current version, no DDL re-run; empty Postgres → all migrations applied; corrupt `_migrations` → boot aborts with clear error | `src/lib/observation-log/migrations.test.ts` (new) |
| Postgres backend | `insert` + `query` round-trip; per-user filtering; ISO date filter parity with SQLite; close behavior | `src/lib/observation-log/postgres.test.ts` (new) — uses `pg-mem` if it covers our DDL/queries; falls back to `testcontainers` if Postgres-specific syntax breaks `pg-mem` |
| SQLite backend | Existing v0.6 tests, mechanically lifted | `src/lib/observation-log/sqlite.test.ts` (renamed) |
| Public lib | Backend selection logic (DATABASE_URL set/unset → right engine instantiated). Mock both engines; verify dispatch | `src/lib/observation-log.test.ts` (rewritten) |
| Scope enforcement | Each MCP method × each scope combination → expected allow/deny + correct WWW-Authenticate header on deny; scope-free methods (`initialize`, `ping`) work without any scope | `src/http.test.ts` (extended) |
| End-to-end smoke | All v0.6 paths still pass against SQLite. New: HTTP path against a `pg-mem`-backed test instance with a Logto-shaped HS256 token carrying `scope: "sky-tonight:read sky-tonight:write"`. Reads succeed; remove `sky-tonight:write` from the token and verify `log_observation` returns `-32001`. | [scripts/smoke-test.ts](../../../scripts/smoke-test.ts) (extended) |

We do **not** add tests against the real Logto / Neon / Fly stack. Those are integration-of-third-parties — the v0.6 design (which we follow) draws the line at "verify our code, mock external boundaries."

## Failure modes

| Failure | Detection | Response |
|---|---|---|
| Neon connection times out (cold start, network blip) | `pg` client surfaces timeout error during a request | Return JSON-RPC `-32000` with `data.cause: "storage_unavailable"`. Don't crash the process. Fly machine stays up. |
| Migration fails on boot (Postgres DDL syntax error caught only against real PG) | Runner throws inside the synchronous import path | Process exits non-zero. Fly's healthcheck fails. Previous machine version stays serving until we `flyctl deploy` a fix. Acceptable: better than half-migrated. |
| Logto JWKS fetch fails | v0.6's `verifyBearer` already surfaces this as a 401 | Same path as v0.6. Note in deploy doc that `OAUTH_JWKS_URL` must be reachable from the Fly machine. |
| `better-sqlite3` native build fails in the Docker stage | Build fails at `docker build` time, before deploy | Caught locally in CI. Don't deploy a broken build. |
| Fly machine OOM (256 MB tight) | Fly logs + machine restart loop | Bump to `shared-cpu-1x` 512 MB. Documented in deploy doc as a knob. |
| npm name `sky-tonight` is taken | `npm publish` rejects | Pre-checked at the start of npm publish step. Fall back to `@girishbaranda/sky-tonight`; only the registry entry's package reference changes. No code changes. |
| Registry rejects `server.json` (schema validation) | `mcp-publisher publish` returns errors | Iterate locally with `mcp-publisher validate` before submitting. |
| Logto rate-limits JWKS fetches | Spike of cold-start traffic exceeds free-tier rate | v0.6's `verifyBearer` already caches JWKS in-process. Re-verify the cache TTL is reasonable; bump if not. |

## What v0.7 does NOT add

Mirroring v0.6's closing paragraph — set v0.8 expectations:

- No per-user quotas or rate limits.
- No audit logs of who called what.
- No admin UI for inspecting stored observations.
- No roaming of v0.6 local SQLite data to the hosted Postgres.
- No JSONB indexes on observation notes (notes stay `TEXT`).
- No multi-region replication.
- No self-hosted Logto recipe (Logto Cloud only).

v0.8 candidates that came up during this design's brainstorming and got deferred: scope-by-resource selectivity (e.g. `sky-tonight:log:read` separate from `sky-tonight:catalog:read`), an observation-data export tool, observation tagging.
