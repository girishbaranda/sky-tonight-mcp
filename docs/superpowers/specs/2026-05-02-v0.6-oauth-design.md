# v0.6 — OAuth 2.1 (Resource Server)

**Status:** spec
**Date:** 2026-05-02
**Lesson this version teaches:** the MCP server is an OAuth 2.1 **Resource Server**. It advertises auth metadata, validates Bearer tokens, and partitions per-user data — without becoming an Authorization Server itself. Same eleven `register*()` calls, same `createMcpServer()` factory, gated at the transport boundary.

## Goal

Add OAuth 2.1 to the HTTP transport so multi-user remote deployments are possible. Per-user data (the observation log) gets scoped by the JWT's `sub` claim. Public computation tools and read-only catalogs remain conceptually public — every authenticated user sees the same Messier data — but every HTTP request still requires a valid Bearer token. Stdio is unchanged: it continues to run as a host-spawned subprocess with no auth, scoping all log rows to a constant `"local"` user.

## Non-goals

- **Authorization Server endpoints.** No `/authorize`, `/token`, no PKCE, no Dynamic Client Registration. Sky-tonight is a Resource Server only. Token issuance is delegated to an external IdP (production) or a tiny in-repo dev minter (local development).
- **Per-tool selectivity.** Auth is uniform across the HTTP surface — every `tools/call`, `resources/read`, `prompts/get` requires a valid token. "Public catalogs stay public" is conceptual (every user sees the same data), not unauthenticated-public. The PRM doc advertises scopes for v0.7+ to layer onto, but v0.6 does not gate by scope.
- **HTTPS termination.** The Node `http` server still speaks plaintext. Production users put it behind nginx / Caddy / a tunnel.
- **Refresh tokens, token revocation, audit logs.** Out of scope; v0.7+ may revisit.
- **Multi-resource `aud` negotiation.** RFC 8707 resource indicators beyond a single configured audience string are deferred.
- **Origin allowlist on CORS.** Liberal `Access-Control-Allow-Origin: <echo>`. Auth is the gate.
- **New tools or resources.** v0.6 adds zero new MCP surface. It only changes how existing surface is gated and scoped.
- **Replacing stdio's behavior.** Stdio entry stays auth-free. The trust boundary there is the OS user.

## Architecture

Three new files, three edits, one new dependency.

### New: `src/lib/auth.ts`

Single source of truth for JWT validation. Pure module, no HTTP concerns.

```ts
export interface AuthConfig {
  mode: "hs256" | "jwks";
  secret?: Uint8Array;        // hs256
  jwksUrl?: string;           // jwks
  issuer?: string;            // jwks (required when mode=jwks)
  audience?: string;          // jwks (required when mode=jwks)
}

export interface AuthContext {
  userId: string;             // jwt.sub
  scopes: string[];           // jwt.scope split on spaces (empty array if absent)
  rawClaims: Record<string, unknown>;
}

export function loadAuthConfig(env: NodeJS.ProcessEnv): AuthConfig;
export async function verifyBearer(token: string, cfg: AuthConfig): Promise<AuthContext>;
```

`loadAuthConfig`:
- `DEV_JWT_SECRET` set, `OAUTH_JWKS_URL` unset → `mode: "hs256"`, `secret: TextEncoder().encode(DEV_JWT_SECRET)`.
- `OAUTH_JWKS_URL` set, `DEV_JWT_SECRET` unset → `mode: "jwks"`, requires `OAUTH_ISSUER` + `OAUTH_AUDIENCE` to also be set; throws otherwise.
- Both set → throws `"DEV_JWT_SECRET and OAUTH_JWKS_URL are mutually exclusive — pick one"`.
- Neither set → throws `"set either DEV_JWT_SECRET (dev) or OAUTH_JWKS_URL+OAUTH_ISSUER+OAUTH_AUDIENCE (prod)"`.

`verifyBearer` uses the [`jose`](https://github.com/panva/jose) library (RFC-compliant JOSE/JWT, ESM-native, ~50KB, MIT). HS256: `jose.jwtVerify(token, cfg.secret)`. JWKS: `jose.jwtVerify(token, jose.createRemoteJWKSet(new URL(cfg.jwksUrl)), { issuer, audience })`. The remote JWKS handle is built once per `AuthConfig` and reused; `jose` handles caching and key rotation internally.

Claim requirements:

| Claim | HS256 mode | JWKS mode |
|---|---|---|
| `iss` | not checked | must match `OAUTH_ISSUER` |
| `aud` | not checked | must match `OAUTH_AUDIENCE` |
| `exp` | required, future | required, future |
| `nbf` | optional; if present, must be past | same |
| `sub` | required, non-empty string | required, non-empty string |
| `scope` | parsed if present, ignored for gating | same |

`sub` is the only claim that affects behavior — it becomes `userId`. We accept any non-empty string as opaque (`"local-dev"`, `"github|123456"`, `"alice@example.com"`, UUIDs all fine).

### New: `src/lib/user-context.ts`

```ts
import { AsyncLocalStorage } from "node:async_hooks";

const storage = new AsyncLocalStorage<{ userId: string }>();

export function runWithUser<T>(userId: string, fn: () => T): T {
  return storage.run({ userId }, fn);
}

export function currentUserId(): string {
  const ctx = storage.getStore();
  if (!ctx) throw new Error("currentUserId() called outside runWithUser scope");
  return ctx.userId;
}
```

Used by stdio entry, HTTP handler, and the two log-touching tool handlers. Chosen over threading `userId` through every `register*()` signature because that refactor would touch nine files for a thing only two tools care about. ALS is well-supported (Node 16+) and our call rate has no perf concerns.

### New: `scripts/mint-dev-token.ts`

```ts
#!/usr/bin/env node
/**
 * Dev-only HS256 token minter. Refuses to run if DEV_JWT_SECRET is unset.
 * NEVER use in production — anyone with the secret can forge tokens.
 *
 * Usage: DEV_JWT_SECRET=test npm run mint-token -- --sub alice --exp 86400
 *        DEV_JWT_SECRET=test npm run mint-token   # defaults: sub=local-dev, exp=24h
 */
import { SignJWT } from "jose";

const secret = process.env.DEV_JWT_SECRET;
if (!secret) {
  console.error("DEV_JWT_SECRET is not set. Refusing to mint a token.");
  process.exit(1);
}

// Tiny CLI flag parsing — no minimist dep.
const args = new Map<string, string>();
for (let i = 2; i < process.argv.length; i += 2) {
  const k = process.argv[i]?.replace(/^--/, "");
  const v = process.argv[i + 1];
  if (k && v) args.set(k, v);
}
const sub = args.get("sub") ?? "local-dev";
const expSeconds = Number(args.get("exp") ?? 86400);

const token = await new SignJWT({})
  .setProtectedHeader({ alg: "HS256" })
  .setSubject(sub)
  .setIssuedAt()
  .setExpirationTime(`${expSeconds}s`)
  .sign(new TextEncoder().encode(secret));

console.log(token);
```

### Edited: `src/http.ts`

Pre-`handleRequest` middleware adds:

1. **PRM endpoint** — `GET /.well-known/oauth-protected-resource` returns `200 application/json` with the PRM document (see "PRM document" below). No auth.
2. **CORS preflight** — `OPTIONS /mcp` returns `204` + CORS headers. No auth.
3. **Bearer extraction + verification** — for `POST /mcp`:
   - No `Authorization` header → `401` + `WWW-Authenticate: Bearer realm="sky-tonight", resource_metadata="<absolute PRM URL>"`. Empty body.
   - Header present but not `Bearer <token>` form → `401` + `WWW-Authenticate: Bearer realm="sky-tonight", error="invalid_request", resource_metadata="..."`.
   - `verifyBearer` throws → `401` + `WWW-Authenticate: Bearer realm="sky-tonight", error="invalid_token", error_description="<sanitized>", resource_metadata="..."`. The `error_description` is mapped from the `jose` error code to one of a fixed set: `"expired"`, `"invalid signature"`, `"invalid audience"`, `"invalid issuer"`, `"not yet valid"`, `"missing sub"`, `"invalid token"`. Anything unmapped collapses to `"invalid token"`. Raw `jose` messages never reach the client (they sometimes echo claim values).
   - Success → `runWithUser(authCtx.userId, () => existing handleRequest path)`.

CORS headers (attached to PRM response, OPTIONS preflight, and POST response):
- `Access-Control-Allow-Origin: <echo of Origin header>` — header is set only when the request carries an `Origin`. Non-CORS callers (curl, server-to-server) get no `Allow-Origin` header, which is correct.
- `Access-Control-Allow-Methods: POST, OPTIONS, GET`
- `Access-Control-Allow-Headers: Content-Type, Authorization, MCP-Protocol-Version`
- `Access-Control-Max-Age: 600`
- `Vary: Origin`

`startHttpServer` signature gains an optional `authConfig`:

```ts
export function startHttpServer({
  host,
  port,
  authConfig,
}: {
  host: string;
  port: number;
  authConfig?: AuthConfig;  // defaults to loadAuthConfig(process.env)
}): Promise<http.Server>;
```

Tests inject an HS256 config without polluting `process.env`. The CLI entry point (the `if (process.argv[1] === ...)` block) still calls `loadAuthConfig(process.env)` with no argument.

The PRM URL the response advertises is built from the request: scheme is `req.headers["x-forwarded-proto"]` if present (operator's reverse proxy populates it), else `http`. Host is `req.headers.host`, falling back to the configured bind `host:port` if absent. So a localhost dev advertises `http://127.0.0.1:3000/.well-known/oauth-protected-resource`, and a behind-Caddy production advertises `https://sky-tonight.example.com/.well-known/oauth-protected-resource` automatically.

### Edited: `src/lib/observation-log.ts`

Schema:

```sql
CREATE TABLE IF NOT EXISTS observations (
  id           INTEGER PRIMARY KEY,
  user_id      TEXT    NOT NULL,
  observed_at  TEXT    NOT NULL,
  latitude     REAL    NOT NULL,
  longitude    REAL    NOT NULL,
  target       TEXT    NOT NULL,
  notes        TEXT,
  seeing       INTEGER,
  transparency INTEGER,
  equipment    TEXT,
  created_at   TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_obs_user_observed_at ON observations(user_id, observed_at);
CREATE INDEX IF NOT EXISTS idx_obs_target_lower ON observations(LOWER(target));
```

Migration in `openDb`:

```ts
const cols = conn.prepare("PRAGMA table_info(observations)").all() as { name: string }[];
const hasUserId = cols.some((c) => c.name === "user_id");
if (cols.length > 0 && !hasUserId) {
  conn.exec(`ALTER TABLE observations ADD COLUMN user_id TEXT NOT NULL DEFAULT 'local'`);
}
// Index creation is idempotent (IF NOT EXISTS) — safe to run on every open.
```

Important: the `DEFAULT 'local'` is only applied during the `ALTER TABLE` migration so existing rows backfill cleanly. New tables created by the `CREATE TABLE IF NOT EXISTS` above don't have a DEFAULT — every insert must supply a `user_id`. SQLite's `ALTER TABLE ADD COLUMN ... DEFAULT 'local'` populates existing rows with `'local'` and the column is `NOT NULL`-enforced for future inserts; the absence of a DEFAULT in the `CREATE TABLE` statement means new-DB inserts crash loudly if a caller forgets to pass `userId`.

## Behavior

### PRM document

`GET /.well-known/oauth-protected-resource` returns `200 application/json`, no auth required:

```json
{
  "resource": "<scheme>://<host>/mcp",
  "authorization_servers": ["<OAUTH_ISSUER, or 'https://dev.local/oauth' in HS256 mode>"],
  "bearer_methods_supported": ["header"],
  "scopes_supported": ["sky-tonight:log:read", "sky-tonight:log:write"],
  "resource_documentation": "https://github.com/girishbaranda/sky-tonight-mcp"
}
```

`scheme` and `host` are resolved per-request as described in the `src/http.ts` section, so the same binary serves correct PRM data in localhost dev (`http://127.0.0.1:3000/mcp`) and in production behind a reverse proxy (`https://sky-tonight.example.com/mcp`). In HS256 mode `authorization_servers` lists a placeholder string; the README explains that PRM in dev mode is non-functional for discovery — the lesson is the *shape*, not a working flow.

Scopes are advertised but not enforced in v0.6. Listing them keeps the doc RFC-shaped and gives v0.7+ a vocabulary to layer on without a metadata change.

### Stdio `user_id`

Hardcoded to the literal string `"local"`. No env override. Rationale: an env override would let one OS user impersonate another in DB rows that survive sharing — a footgun for zero gain in a single-user tool. Multi-user on a shared machine is the HTTP path with a real token.

### CORS

Liberal echo. No origin allowlist in v0.6. Auth is the gate. Operators wanting tighter origin control put it at the reverse proxy.

### Errors

- Server boot, no auth env vars → `console.error` clear message naming both var groups, `process.exit(1)`. (HTTP path only — stdio is untouched.)
- Server boot, both auth env vars set → same fail-fast pattern, message names both vars.
- JWKS fetch failure at runtime → `401` with `error="server_error"`. Fail closed; no stale-key fallback.
- Malformed `Authorization` header (`Basic ...`, missing scheme) → `401` with `error="invalid_request"`.

### Logging

Stdio: unchanged.
HTTP:
- Success: `console.error("[http] POST /mcp sub=${userId} 200")`.
- Auth failure: `console.error("[http] POST /mcp 401 (${reason})")` — never logs token contents, only the *reason* (`expired`, `bad signature`, `missing audience`, etc.).

Stderr-only matches the v0.1 stance.

### Concurrency

Per-request `runWithUser` scope means concurrent HTTP requests for different users have isolated `userId` context inside their respective handlers. `AsyncLocalStorage` guarantees this by tying context to the async chain rooted at the request handler.

## Tests

### `src/http.test.ts` — extended

Each case spins up its own `startHttpServer` on `port: 0` with an injected HS256 `authConfig` (ephemeral secret) and `SKY_TONIGHT_DB=":memory:"`:

1. **PRM endpoint** — `GET /.well-known/oauth-protected-resource` returns `200`, JSON has `resource`, `authorization_servers`, `bearer_methods_supported: ["header"]`. No auth required.
2. **Missing auth → 401** — `POST /mcp` with no header. `WWW-Authenticate` includes `resource_metadata` parameter.
3. **Bad token → 401** — random garbage. `WWW-Authenticate` includes `error="invalid_token"`.
4. **Expired token → 401** — token with `exp` 60s in the past.
5. **Wrong-secret token → 401** — token signed with a different HS256 secret.
6. **Valid token → 200** — `sub: "alice"`, `tools/call moon_phase` succeeds.
7. **Per-user log isolation** — token A logs an observation; token B's `recall_log` returns empty; token A's `recall_log` returns the row. The primary v0.6 lesson at the wire level.
8. **CORS preflight** — `OPTIONS /mcp` returns `204` + Access-Control-* headers. `POST /mcp` response also carries CORS headers.
9. **Boot validation** — pure unit test on `loadAuthConfig`: `loadAuthConfig({})` throws; `loadAuthConfig({ DEV_JWT_SECRET: "x", OAUTH_JWKS_URL: "..." })` throws; `loadAuthConfig({ DEV_JWT_SECRET: "x" })` returns `mode: "hs256"`.

No JWKS-mode integration test in v0.6. Standing up a fake AS or mocking `jose`'s remote-key fetcher adds weight for one branch. The unit tests of `loadAuthConfig` cover the config wiring; the JWKS verification path is exercised by `jose`'s own test suite upstream.
