# v0.3 — Prompts — Design

**Date:** 2026-05-01
**Status:** Approved (pending spec review)
**Roadmap step:** v0.3 in [README.md](../../../README.md)

## Goals

Add the MCP **Prompts** primitive to sky-tonight by registering three prompt templates that compose the existing tools and v0.2 resources into curated, slash-invocable workflows.

v0.1 demonstrated **Tools**. v0.2 demonstrated **Resources**. v0.3 demonstrates **Prompts** — and shows how the three primitives compose: a Prompt is a templated user message that instructs the LLM how to call Tools and read Resources to accomplish a higher-level task.

The three prompts:

1. `plan_tonight_session(duration_min, skill_level)` — curated observing plan tying together moon, planets, deep-sky, and ISS.
2. `identify_object(description)` — open-ended "what was that?" workflow driven by a free-text observation.
3. `tour_constellation(name)` — visibility-aware walk through one constellation's stars and Messier objects.

Each prompt exercises a distinct shape (curated workflow / open-ended ID / catalog-driven tour) so a reader of the codebase sees Prompts deployed in three different ways.

## Non-goals

- **Prompt arguments for location.** All three prompts could take `lat`/`lon`, but the slash-command form would force every invocation to repeat them. Location is handled conversationally — the prompt body instructs the LLM to ask if it doesn't already know.
- **External markdown files for prompt bodies.** Inline TS template literals are used instead, mirroring how tool descriptions are written today. Keeps the file count and reading order consistent with v0.1/v0.2.
- **More than three prompts.** The set is deliberate; adding a fourth would dilute the lesson.
- **Auto-execution / tool calls inside the prompt template.** MCP prompts return *messages*, not actions. The LLM decides when to call which tool based on the prompt body's instructions.
- **Persistent observation log** (v0.4), **Streamable HTTP transport** (v0.5), **OAuth** (v0.6).

## Prompts

All three are registered via `server.registerPrompt(name, metadata, handler)`. Each handler returns:

```ts
{
  messages: [
    { role: "user", content: { type: "text", text: "...templated body..." } },
  ],
}
```

The `metadata.description` is what shows in the slash-command picker — keep it short and concrete (one sentence). The body text is what gets injected as a user message into the LLM's context.

### Argument schemas

MCP prompt arguments are defined as a record of Zod string schemas (the SDK serializes to JSON Schema with simple string types — prompt args don't support numbers/enums natively at the protocol level, so numeric values arrive as strings and the prompt body parses them). Where a constrained value is needed, the body text spells out the allowed values rather than relying on protocol-level enforcement.

### Prompt: `plan_tonight_session`

**Arguments:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `duration_min` | string | yes | Minutes the user has. Body parses to int. |
| `skill_level` | string | yes | One of `beginner`, `intermediate`, `advanced`. Body validates and explains if invalid. |

**Body** (returned as one `user`-role message):

> You are helping plan a {duration_min}-minute backyard observing session for a {skill_level} observer.
>
> **Step 1 — Location.** If you don't already know the user's latitude/longitude, ask before doing anything else. All tools below require it.
>
> **Step 2 — Conditions.** Call `moon_phase` to get illumination. A bright Moon (>50% illumination) washes out faint deep-sky targets — note this in the plan.
>
> **Step 3 — Easy wins (always include).** Call `objects_visible_tonight` to list planets and the Moon visible during astronomical night, ranked by altitude. Pick the top 2–3 for the plan.
>
> **Step 4 — Deep sky.** Call `deep_sky_visible_tonight` with these parameters tuned to skill level (note: `type_filter` accepts a single value — one of `galaxy`, `nebula`, or `cluster` — not an array):
> - `beginner`: `max_magnitude: 6`, optionally `type_filter: "cluster"` (open and globular clusters are visually rewarding for unaided/binocular observers); pick 2 targets max. If you want a brighter nebula too, run a second call with `type_filter: "nebula"`.
> - `intermediate`: `max_magnitude: 8`, no type filter; pick 3–4 targets.
> - `advanced`: `max_magnitude: 10`, no type filter; pick 4–6 targets including any galaxies.
>
> **Step 5 — ISS bonus.** Call `iss_passes` for the next 24 hours. If a pass starts within the session window, slot it in.
>
> **Step 6 — Build the plan.** Allocate ~{duration_min}/N minutes per target. Order by best-time-to-observe (highest altitude). For each target output: name, what it is, where to look (compass + altitude), why it's worth seeing.
>
> **Style by skill level:**
> - `beginner`: visual analogies ("looks like a fuzzy patch of stars"), no jargon, recommend naked-eye / binoculars.
> - `intermediate`: include magnitudes, brief structural detail, suggest scope size.
> - `advanced`: include RA/Dec, transit times, structural notes (e.g. "edge-on spiral, dust lane visible at >150x").
>
> If the Moon is up and bright, suggest a Moon-friendly section first (lunar features, double stars, bright planets) before dimmer targets later in the session.
>
> If no astronomical night occurs at this latitude/date (polar summer), fall back to civil-twilight planets and the Moon.

**Validation:** if `skill_level` is not one of the three accepted values, the prompt body opens with: "The skill_level argument must be one of: beginner, intermediate, advanced. The user provided: {skill_level}. Ask the user to clarify or proceed assuming intermediate."

### Prompt: `identify_object`

**Arguments:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `description` | string | yes | Free-text dump. The body instructs the LLM to extract direction / altitude / time / motion / color clues. |

**Body:**

> The user is trying to identify something they saw in the sky. Their description:
>
> > {description}
>
> **Step 1 — Location & time.** All tools require lat/lon. Ask if you don't know the user's location. Extract the observation time from the description if mentioned (e.g. "around 9pm tonight"). If absent, ask.
>
> **Step 2 — Extract observable clues.** From the description, identify any of: compass direction (N/NE/E/...), altitude (low/mid/high or degrees), color, brightness ("very bright", "dim"), motion (twinkling, moving, flashing), shape (point, fuzzy, elongated). State the clues you found in one short paragraph.
>
> **Step 3 — Rule out fast-moving objects first.**
> - If the user reported steady motion across the sky over seconds-to-minutes → call `iss_passes` for the observation time. The ISS is the most likely candidate for a slow, bright, non-blinking moving point.
> - If the user reported blinking lights → almost certainly an aircraft. Say so plainly and stop.
> - If the user reported a brief streak (sub-second) → meteor. Say so plainly and stop.
>
> **Step 4 — Match against tonight's sky.** Call `objects_visible_tonight` with `min_altitude_deg: 5` to get all planets + Moon visible at the observation time. Compare magnitude and direction against the user's description. The Moon and Venus are by far the most common "what was that bright thing" candidates.
>
> **Step 5 — Deep-sky check (only if relevant).** If the user described something fuzzy / non-pointlike, call `deep_sky_visible_tonight` to see what's up. Most naked-eye fuzzy reports are M31 (Andromeda), M42 (Orion Nebula), M45 (Pleiades), or the Milky Way — match by direction.
>
> **Step 6 — Conclusion.** Lead with the single most likely match and your confidence ("Almost certainly Venus", "Probably Jupiter, possibly Saturn"). Cite the matching evidence (magnitude, direction, altitude). If the description is too sparse, ask one targeted follow-up question (the single most discriminating one — usually direction or whether it was moving) rather than guessing.
>
> **Don't:** speculate about UFOs, satellites other than the ISS (we don't have TLE data for them), or things not derivable from the tools above.
>
> If nothing in the visible-tools' output matches, tell the user honestly that you can't match it from the available data, and suggest what additional detail would help.

### Prompt: `tour_constellation`

**Arguments:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | yes | Constellation name OR IAU 3-letter abbreviation. Case-insensitive. Body instructs LLM to suggest closest matches if not found. |

**Body:**

> The user wants a tour of the constellation: **{name}**.
>
> **Step 1 — Resolve the constellation.** Read `sky://catalog/constellations` to find the matching entry by name or IAU abbreviation. If no match, tell the user and suggest the closest names from the index. Once matched, read `sky://constellation/{abbr}` for the full record. The record contains: `name`, `latin_genitive`, `abbreviation`, `hemisphere` (northern/southern/equatorial), `best_months`, `brightest_star` (a single `{name, magnitude}` object — NOT a list), `notable_objects` (string list, often referencing Messier IDs), and `story`. There are no RA/Dec fields on this record — for individual star positions, rely on your general astronomy knowledge.
>
> **Step 2 — Location.** Ask for lat/lon if you don't already know it.
>
> **Step 3 — Visibility check.** Call `objects_visible_tonight` to confirm astronomical night exists tonight at the user's location. Then determine if the constellation is currently up by calling `deep_sky_visible_tonight` and looking at the bracketed `[type in Constellation]` suffix on each result line — if any line ends in this constellation's name, it's at least partially up. Combine with `hemisphere` from the resource and the user's latitude as a sanity check (e.g. Crux is unreachable from above ~25°N).
>
> **Step 4a — If visible tonight:**
>   1. Name the constellation's brightest star using `brightest_star.name` from the resource. Mention 2–4 other principal stars from your general knowledge (e.g. for Orion: Rigel, Betelgeuse, Bellatrix, the Belt). Describe their positions qualitatively relative to each other ("Belt is the line of three; Betelgeuse marks the upper-left shoulder") rather than giving alt/az — we don't have a star-position tool. If `objects_visible_tonight` reports a planet near the constellation, use it as a compass anchor.
>   2. Take the `notable_objects` list from the resource as a starting point, then read `sky://catalog/messier` and filter the index to objects whose `constellation` field matches this constellation's name. Call `deep_sky_visible_tonight` and intersect — keep only the objects from the constellation that the tool reports as up tonight at observable altitude.
>   3. Build the tour: brightest star first → asterism / shape → 1-3 deep-sky highlights, in the order a user would naturally pan across the sky.
>
> **Step 4b — If NOT visible tonight:**
>   1. Say so plainly: "Cygnus isn't visible from your location tonight."
>   2. From the resource's `best_months`, tell the user when it returns to the evening sky.
>   3. Optionally call `objects_visible_tonight` and offer 2-3 alternatives that ARE up tonight in the same general direction.
>   4. Still summarize what the constellation contains (brightest stars, notable Messier objects) so the user learns about it — just frame it as preview rather than tour.
>
> **Style:** plain language by default. Include star names (Betelgeuse, Rigel) and Messier IDs (M42, M43). Skip RA/Dec unless the user asks for it. Mention mythology briefly if the resource record includes it.
>
> **Edge cases:**
> - Constellation name typo / not found → suggest closest matches from the index resource.
> - Latitude makes constellation never visible (e.g. Crux from northern Europe) → say so and explain the latitude limit.

## How prompts compose with v0.1 and v0.2

Each prompt is a thin orchestration layer over existing tools and resources. No new tools, no new resources, no new data files. The prompt bodies reference existing capabilities by exact name:

| Prompt | Tools referenced | Resources referenced |
|---|---|---|
| `plan_tonight_session` | `moon_phase`, `objects_visible_tonight`, `deep_sky_visible_tonight`, `iss_passes` | — |
| `identify_object` | `iss_passes`, `objects_visible_tonight`, `deep_sky_visible_tonight` | — |
| `tour_constellation` | `objects_visible_tonight`, `deep_sky_visible_tonight` | `sky://catalog/constellations`, `sky://constellation/{abbr}`, `sky://catalog/messier` |

If a referenced tool/resource is renamed in the future, the corresponding prompt body must be updated. This is acceptable coupling — it's the entire point of prompts.

## Testing

Extend `scripts/smoke-test.ts` with three new checks. The existing v0.1 + v0.2 tests stay unchanged and must continue to pass.

1. **`prompts/list`** — send the JSON-RPC request and assert exactly 3 entries with names `plan_tonight_session`, `identify_object`, `tour_constellation`. For each, assert the declared arguments match the spec (e.g. `plan_tonight_session` declares `duration_min` and `skill_level` as required; `identify_object` declares `description` as required; `tour_constellation` declares `name` as required).
2. **`prompts/get` happy path** — for each of the three prompts, send `prompts/get` with valid sample arguments (`{duration_min: "120", skill_level: "intermediate"}`, `{description: "bright dot in the southwest at 9pm"}`, `{name: "Orion"}`). Assert the response contains a non-empty `messages` array, the first message has `role: "user"`, and the text body contains the substituted argument values.
3. **`prompts/get` argument substitution** — assert the returned text actually interpolates arguments (e.g. `plan_tonight_session` body contains "120-minute" and "intermediate"; `tour_constellation` body contains "Orion").

We do NOT test the *behavior* downstream of the prompt (whether the LLM follows the instructions correctly) — that's an LLM eval, not an MCP protocol test. The smoke test verifies the prompt is registered, args are declared, and the templated body is returned. That's the contract this server owns.

## Open questions

None at spec time. All design decisions resolved during brainstorming:

- Scope: 3 prompts (B), set A from the picker.
- Location: handled conversationally, not as args.
- `skill_level`: dual-purpose (target difficulty + explanation depth).
- `identify_object` arguments: single free-text `description`.
- `tour_constellation` arguments: single `name`, visibility-aware behavior.
- File layout: one file per prompt, mirroring `tools/` and `resources/`.
- Prompt body format: inline TS template literals, not external markdown.
