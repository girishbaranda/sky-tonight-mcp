# v0.4 — Persistent observation log

**Status:** spec
**Date:** 2026-05-01
**Lesson this version teaches:** the server becomes *stateful* — the first time data persists across MCP sessions.

## Goal

Add two MCP tools, `log_observation` and `recall_log`, backed by a local SQLite database. With this in place the server can answer questions like "what did I see last weekend?" or "have I logged Jupiter at seeing ≥4?" — questions that the existing pure-compute tools structurally cannot answer.

The diff is intentionally small. The point is *statefulness*, not a fully featured observing log. Domain richness can grow in v0.4.x.

## Non-goals

- Multi-user / per-user scoping. That is v0.6 (OAuth).
- Remote DB. Stays local until v0.5 (HTTP transport) and v0.6.
- Editing or deleting observations. Write + read is enough to demonstrate persistence; deletion has its own design surface (soft vs hard, confirmation flow) that is out of scope here.
- Sync / replication / conflict resolution.
- Migrations / schema versioning. v0.4 is the first schema. If v0.4.1 changes it, that is when we introduce `PRAGMA user_version`.
- A `sky://log/...` Resource view. Could be a clean follow-up; not required for the v0.4 lesson.

## Tool surface

### `log_observation`

Writes one row, returns the assigned id and a one-line confirmation.

| Field | Required | Type | Notes |
|---|---|---|---|
| `target` | ✓ | string | Free text: `"M31"`, `"Jupiter"`, or `"bright dot low SW"`. |
| `latitude` | ✓ | number, -90..90 | |
| `longitude` | ✓ | number, -180..180 | |
| `timestamp` | – | ISO string | Defaults to now. |
| `notes` | – | string | |
| `seeing` | – | int 1..5 | Atmospheric steadiness. |
| `transparency` | – | int 1..5 | Sky clarity. |
| `equipment` | – | string | E.g. `"naked eye"`, `"10x50 binoculars"`, `"8\" Dob"`. |

Returns text content along the lines of:

```
Logged observation #42: Jupiter at 23.22, 72.64 on 2026-05-01T18:30:00Z (seeing 4, 8" Dob)
```

### `recall_log`

Returns matching rows, newest first.

| Filter | Type | Notes |
|---|---|---|
| `target` | string | Substring match, case-insensitive. Omit to see all. |
| `since` | ISO date | Inclusive lower bound on `observed_at`. |
| `until` | ISO date | Inclusive upper bound on `observed_at`. |
| `min_seeing` | int 1..5 | Excludes both `seeing IS NULL` and `seeing < N`. |
| `limit` | int | Default 20, max 100, must be ≥1. |

Returns text content: a one-line summary of the filters that ran, then one line per row. Empty result is not an error — returns `"No observations match those filters."` plus the summary so the LLM/user sees what was searched.

The lib is the only place that imports `better-sqlite3` or contains SQL. Tool files stay thin — argument validation in / text formatting out — same shape as the existing four tools.

**Naming convention.** Tools follow the existing wire convention (`timestamp`, `min_seeing`, `latitude`, `longitude` — snake_case as in `objects-visible.ts`). The lib is internal JS and uses camelCase (`observedAt`, `minSeeing`). The mapping happens explicitly inside each tool's handler (one line each) — a deliberate, visible boundary, not silent magic.

## Lib surface

```ts
// src/lib/observation-log.ts

export interface ObservationInput {
  target: string;
  latitude: number;
  longitude: number;
  observedAt?: Date;     // defaults to now
  notes?: string;
  seeing?: number;       // 1..5
  transparency?: number; // 1..5
  equipment?: string;
}

export interface Observation {
  id: number;
  target: string;
  latitude: number;
  longitude: number;
  observedAt: string;    // ISO
  notes: string | null;
  seeing: number | null;
  transparency: number | null;
  equipment: string | null;
  createdAt: string;     // ISO
}

export interface RecallFilters {
  target?: string;       // substring, case-insensitive
  since?: Date;
  until?: Date;
  minSeeing?: number;
  limit?: number;        // default 20, capped at 100, must be >= 1
}

export function logObservation(input: ObservationInput): Observation;
export function recallObservations(filters: RecallFilters): Observation[];

// Test-only helpers, not consumed by tools:
export function _resetForTest(dbPath?: string): void;  // closes & reopens; accepts ":memory:"
export function _closeForTest(): void;
```

**Tools only see this surface.** They do not import `Database` from `better-sqlite3`, do not see row shapes from the driver, and do not write SQL. That boundary is what makes the future Postgres swap mechanical (see *Future: Postgres swap* below).

## Database

### Library

`better-sqlite3`. Synchronous, fast, ergonomic. Prebuilt binaries cover macOS/Linux/Windows on common Node versions, so `npm install` stays a one-liner. Sync API keeps handlers uncluttered — the only new concept readers absorb is "the server is stateful," not async query plumbing.

Add to `package.json`:

```json
"dependencies": {
  "better-sqlite3": "^11.5.0"
},
"devDependencies": {
  "@types/better-sqlite3": "^7.6.11"
}
```

(Pin to whatever the current major is at implementation time — the numbers above are the stable line as of writing.)

### Location

Path resolution, in order:

1. `process.env.SKY_TONIGHT_DB` if set. Pass-through; in particular `:memory:` works for tests.
2. Default: `~/.sky-tonight/observations.db`.

The lib `mkdir -p`'s the parent directory on first open. XDG-correct paths can come later if/when the project is published.

### Open / pragmas

Lazy singleton at module scope: opens on first `logObservation` / `recallObservations` call, reused thereafter. PRAGMAs set on open:

- `journal_mode = WAL` — better read concurrency, safe for multi-process readers (e.g. two MCP hosts).
- `foreign_keys = ON` — habit; no FKs in v0.4 but the right default.

### Schema

```sql
CREATE TABLE IF NOT EXISTS observations (
  id           INTEGER PRIMARY KEY,
  observed_at  TEXT    NOT NULL,        -- ISO 8601 UTC, ms precision (Date#toISOString)
  latitude     REAL    NOT NULL,
  longitude    REAL    NOT NULL,
  target       TEXT    NOT NULL,
  notes        TEXT,
  seeing       INTEGER,                 -- 1..5 or NULL
  transparency INTEGER,                 -- 1..5 or NULL
  equipment    TEXT,
  created_at   TEXT    NOT NULL         -- ISO 8601 UTC, ms precision; computed in JS
);

CREATE INDEX IF NOT EXISTS idx_obs_observed_at ON observations(observed_at);
CREATE INDEX IF NOT EXISTS idx_obs_target_lower ON observations(LOWER(target));
```

Notes:

- `id INTEGER PRIMARY KEY` (no `AUTOINCREMENT`). Gets rowid semantics in SQLite; mechanical swap to `BIGSERIAL` / `GENERATED ALWAYS AS IDENTITY` in Postgres.
- `created_at` is computed in JS and passed as a parameter, not via `DEFAULT (strftime(...))`. Keeps the schema portable.
- `LOWER(target)` expression index supports case-insensitive substring match without a full-table scan once the log grows. Both SQLite and Postgres support expression indexes.

## Error handling

Three failure modes:

1. **DB open failure** (permissions, disk, corrupt file). Surfaces on first call. Tools catch and return `{ isError: true, content: [...] }` with the underlying message — same pattern `iss-passes.ts` already uses for network failures. The server keeps running; one broken tool does not take down the other six.
2. **Constraint violations** (e.g. `seeing` outside 1..5). Caught at the Zod layer in the tool — `z.number().int().min(1).max(5)` — so they never reach SQL. The lib trusts validated input.
3. **Empty result set on `recall_log`.** Not an error. Return `"No observations match those filters."` plus a one-line filter summary.

Concurrency: `better-sqlite3` is synchronous within a Node process; with `journal_mode=WAL`, multi-process readers are safe. Concurrent writes serialize at the SQLite level. Sufficient for v0.4.

## Future: Postgres swap

Captured here so we do not re-derive it in v0.5/v0.6.

The public lib surface (`logObservation`, `recallObservations`, the `Observation` / `ObservationInput` / `RecallFilters` types) is the contract. Callers — both tool wrappers and tests — never see the driver. To move to Postgres later:

1. Replace `better-sqlite3` with `pg` (or another Postgres driver). The lib internals change; nothing else does.
2. Translate placeholder syntax `?` → `$1`, `$2`, ... in the prepared statements.
3. Rewrite `id INTEGER PRIMARY KEY` as `id BIGSERIAL PRIMARY KEY` (or `GENERATED ALWAYS AS IDENTITY`).
4. Rewrite the `LOWER(target)` index — Postgres syntax is identical; expression indexes are supported the same way.
5. Connection lifecycle becomes async (`pg` is async), so the lib's exported functions become `async`. This *does* propagate to callers — but only at the `await` keyword level; the call sites are already inside async tool handlers, so the change is one `await` per call, no logic changes.

What we are deliberately *not* doing now: building a repository-interface abstraction with two implementations, or pulling in an ORM. Both pay cost today to save little tomorrow. **Design the boundary, do not build the abstraction.**
